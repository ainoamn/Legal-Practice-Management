# Deployment and operations

Development uses Node 24 LTS and Docker Compose PostgreSQL/Redis. Copy `.env.example` to `.env`, replace DB/Redis secrets, run `docker compose up -d`, `npm ci`, `npm run db:generate`, `npm run db:deploy`, then `npm run dev`. API on 4311, Next on 4310. These ports avoid another existing application on 3000. Only the Next origin should be exposed publicly. Configure WEB_ORIGIN/INTERNAL_API_URL. Next proxy destinations are part of its build configuration; rebuild after changing INTERNAL_API_URL. Cookies need HTTPS in production.

Compose initializes a separate non-superuser runtime database principal. `DIRECT_DATABASE_URL` is migration-only; `DATABASE_URL` is runtime-only. Init scripts run on fresh volumes only. Never grant BYPASSRLS to the runtime principal; never use the migration URL in API. Migration principals need BYPASSRLS (or equivalent administrator capability) to validate new cross-tenant FKs against populated forced-RLS tables. Keep those credentials limited to deployment jobs. Development country catalog is deployable configuration data, not mock case data. Secret `.env` files are ignored.

Platform runtime also requires PLATFORM_DATABASE_URL with the dedicated legal_platform role. The init script creates both runtime principals on fresh volumes. Existing installations must provision that role before the platform migrations; do not erase a volume to rerun initialization. This principal has metadata projections and narrow administrative functions, not access to legal records or office passwords. Startup rejects superuser/BYPASSRLS or direct User/Tenant/Membership SELECT privileges on this connection.

MFA: `npm run security:key` generates 32 random bytes into ignored local .env without printing or replacing a key; use a production secret manager for deployment. Create the first administrator through `npm run admin:bootstrap` and complete mandatory authenticator enrollment at /admin. Loss of the key prevents decrypting authenticator secrets; controlled key recovery belongs in encrypted backup operations. Rotation needs re-encryption before changing the active key.

Tests: `npm run test:setup` creates legal_test and ignored .env.test, with separate DB URLs, Redis DB 1 and MFA key. Test runners require LEGAL_TEST_ENV=1. Development credentials stay in .env. No default platform account or test owner is seeded into a new production database. Development history from initial verification remains preserved; the two earlier fixture administrators were disabled before test isolation was introduced.

Password-recovery mail: configure RESEND_API_KEY and EMAIL_FROM using a verified sending domain. The Mailer boundary can be replaced with SMTP or another provider without changing token logic. Official adapter reference: https://resend.com/docs/api-reference/emails/send-email . Real sending has NOT been verified because no provider key was supplied; automated tests use a mock adapter. Capabilities and UI explicitly show disabled email when unconfigured. No email is sent during tests.

WSL fallback used in this workspace: Ubuntu 24.04 packages PostgreSQL 16.15 and Redis 7.0.15. `infra/dev-bootstrap.sql` creates an empty development database and restricted roles once; it is intentionally not idempotent and must not run against an existing/shared cluster. Local ignored `.env` uses `127.0.0.1:5432` and `redis://127.0.0.1:6379`. Start Ubuntu services with `scripts/start-wsl-services.sh` as root after WSL restarts. Keep a WSL session open while using Windows localhost forwarding. This does not verify the PostgreSQL 18/Redis 8 container images.

The development API binds loopback. Containers set API_HOST=0.0.0.0 and must remain on a private network behind the frontend/ingress. Production ingress must replace forwarding headers; proxy-aware client IP throttling is an outstanding scaling check because the local Next proxy shares a loopback source IP. Account-specific Redis throttling is also enforced.

Staging/production: isolated secrets/databases/buckets, managed PostgreSQL with encrypted disks and TLS, Redis with authentication and TLS, private S3, scanning and job workers. Documents now use the S3 settings in .env.example, BullMQ, ClamAV, Tesseract ara+eng, Poppler and Chromium. The API Dockerfile installs these tools and initializes scanner signatures, but container execution is not verified. Refresh ClamAV signatures with an operational update service/volume; a build-time signature snapshot is insufficient for ongoing production operation. Multi-stage containers run non-root. Run migrations as an owner job before app rollout. Runtime startup probes enforce safe DB roles and forced RLS on 33 business tables. Restrict Swagger and API network access. No production deployment has been performed.

Local S3 verification uses SeaweedFS 4.52 on 127.0.0.1:4320, isolated legal-dev/legal-test buckets, bucket-scoped credentials, and internal read/write JWT keys. The verified Linux asset SHA-256 is 8b538c22d47d0c3fb6792adaa6b0c735a967401270a53427d5a476dcaca9b7ae. Official release: https://github.com/seaweedfs/seaweedfs/releases/tag/4.52 . Run storage:setup after test:setup, then storage:dev separately from the application. It requires the verified weed binary in Ubuntu and does not install system software itself. Windows tools invoke WSL with --exec, bounded timeouts and argv arrays, not user-built shell commands. S3 credentials and generated JWT configuration stay in ignored local files. The local service persists its files under the Ubuntu user's .local/share/legal-s3. Do not treat this single-node, loopback development setup as an encrypted/replicated production service.

CI installs actual scanning/OCR tools and starts a checksum-verified, private S3 test service through scripts/ci-document-services.sh. It writes a test-only .env.test without printing keys. Run test suites sequentially against one environment: global platform configuration and the shared document queue make simultaneous independent integration/E2E processes unsafe. Live document tests have a separate command and are included in check. The configured GitHub workflow itself has not run in this session.

Backup plan: encrypted pg_dump plus WAL/PITR; private object versioning with synchronized metadata snapshots; separate encryption keys; restricted offsite region approved by firm; scheduled restores to isolated infrastructure; compare tenant counts/checksums and ledger balances before marking drills passed. RPO/RTO and retention must be agreed with operator. Backup/restore procedures are planned, not tested yet.

Release checklist: all roadmap gates, real provider configurations, legal review, MFA/recovery, TLS, telemetry without content/secret leakage, support incident runbook, capacity test, restore drill, dependency/security review. Roll back app by immutable image; migrations remain forward-only after use. Do not delete data on subscription expiry.

Hosted preview, 2026-11-04: the Next.js workspace is https://legal-office-web.vercel.app and the Nest API is https://legal-office-api.vercel.app, both in Frankfurt, with PostgreSQL on Neon. The runtime role is NOSUPERUSER and NOBYPASSRLS. Vercel has no Redis in this deployment, so RATE_LIMIT_STORE=postgres uses the RateBucket table. Document scanning, object storage, email, payments, and AI providers are not configured there. This preview is not the production-readiness gate above.
